# Flujo Block Ecosystem Contract

## Status and scope

This contract freezes the maintainer-approved architecture that must exist before Flujo starts producing distributable custom blocks at scale. It sits above the already implemented `BLOCKSDK-001` through `BLOCKSDK-006` foundation and does not replace, duplicate, or reinterpret those contracts.

The original D0 contract delivery was **documentation and governance only**: it
did not add a new graph schema, change `manifest_version = 1`, move the current
integrated blocks, create `flujo-block-builder`, or create the future `IF` block.
The current initial planning Skill is recorded in the continuity status below;
this contract still creates no block or authorizes control-flow implementation.

The approved implementation order is:

`D0 contract → D1 manual SDK profile → D2 minimum Theme + Motion contract → D3 external catalog in Flow Add → D4-A property/presentation contract → D4-B runtime-safe property descriptors → D4-C generic Flusso renderer → D5 flujo-block-builder v1 → D6 first standard external block → D7 package lifecycle → D8 Theme + Motion polish → D9 gradual official-block migration`

### Functional D5 boundary

D5 means a functional `flujo-block-builder v1`, not merely the planning Skill
stored in the repository. D5 is complete only when the Builder can generate and
validate an ordinary one-block package through the public SDK, with deterministic
and manually reproducible output, the standard Flow → Flusso → persistence →
runtime path, no Builder runtime dependency, and no silent Flujo-core patch.
Its acceptance is explicit:

- **A — output:** canonical one-block package with reviewable ordinary files and
  no absolute paths or persistent instance IDs generated by the Builder;
- **B — determinism:** clean reruns and manual recreation are semantically
  equivalent, while invalid or unsupported requests are rejected reproducibly;
- **C — public SDK:** the package uses the same manual contract and validation
  path as official and user/community blocks;
- **D — governance:** every request passes the A/B/C/D capability gate and human
  approval; C/D stops for an approved extension or core plan;
- **E — maintenance:** removing the Skill does not prevent loading, editing,
  testing, maintaining or distributing the generated package.

The current Skill remains the planning/authoring workflow boundary. The approved
FPrint slice is implemented as an ordinary package under
`res://flow_packages/mercury.fprint/`, distinct from legacy `Print`, and uses the
public SDK without a core or registry change. Its automatic discovery, Add,
generic Flusso, persistence, duplication and Process runtime evidence passes;
the manual Godot review is approved and the Guardería slice is closed. Timer,
State Machine and future-container behavior is not claimed.

Closure records:

- `FPRINT GUARDERÍA MANUAL PASS`
- `FPRINT GUARDERÍA CLOSED — EDITOR CLEANUP READY FOR MANUAL REVIEW`

## Current implemented baseline

The following are already implemented and must be reused rather than rebuilt:

- `FlowBlock` persistent identity, display name, enabled state, user note, structural validation hook, internal-reference remap hook and generic navigation hook.
- `FlowOutputBlock` as a shared output contract.
- stable `FlowId` identity and graph-wide duplication/remapping behavior.
- polymorphic `Array[FlowBlock]` persistence through the supported graph schemas.
- `FlowNavigationDecision`, `FlowNavigationContext` and generic Ready execution without concrete custom-block branches.
- external manifest v1, package discovery, script validation, combined editor catalog and external block factory.
- external authoring identity `package_id:type_id`, kept separate from each persistent block instance ID.
- focused tests for manifest, loader, script validation, catalog, factory, generic hooks, navigation and persistence/runtime foundations.

The following are **not** end-to-end implemented yet:

- package-lifecycle recovery for missing scripts/packages;
- the remaining functional D5 Builder v1 acceptance beyond the approved FPrint Guardería slice;
- the future `IF` block.

D4-C generic Flusso property rendering is implemented, automatically covered and
manually approved. The supported D4 v1 boundary is intentionally limited to the
documented scalar types and hints; complex properties, arbitrary widgets and the
future Game Debug Panel remain separate work.

The normal Flow Add authoring path through the external catalog/factory, external
Undo/Redo, the Flusso-owned-property boundary, external persistence/runtime and
the container-independent creation path are D3-complete. Theme, Motion, focus,
layout and standard interaction remain owned by the Fluo host/editor.

## Approved ecosystem requirements

### BLKECO-001 — One distributable block per package

Every distributable block uses one independent package under:

`res://flow_packages/<package_id>/`

Ten distributable blocks therefore use ten packages. A package may be installed, updated, removed, restored or promoted independently without requiring unrelated sibling packages to change.

The manifest v1 loader may continue reading historical manifests that contain multiple block descriptors for compatibility, but the canonical distribution profile and the future builder must generate exactly one distributable block descriptor per package.

### BLKECO-002 — Official and user blocks converge on the same package contract

Official Mercury blocks and user/community blocks must converge on the same public package contract. Official blocks do not receive a privileged runtime format that user blocks cannot reproduce.

The current integrated blocks may remain under `FlowBlockRegistry` during migration. That registry is a compatibility/integration mechanism, **not the intended final home for every distributable official block**.

A later authorized delivery may migrate official blocks one by one to independent `mercury.<block>` packages, preserving historical projects through explicit compatibility shims or migration where needed.

### BLKECO-003 — Manual authoring is first-class

A developer must be able to create, inspect, edit, test and maintain every supported block manually using normal project files, GDScript, JSON and documented public contracts.

No supported block capability may depend exclusively on `flujo-block-builder`.

### BLKECO-004 — `flujo-block-builder` is optional automation

The `flujo-block-builder` Skill may automate package structure, templates, validation, tests and conventions, but it must not introduce secret metadata, private runtime behavior, opaque binaries, hidden registries or capabilities unavailable to manual authors. The initial Skill is planning-gated; it is not the SDK and is not a runtime dependency.

Removing the Skill must not make an already valid package unloadable or unmaintainable.

### BLKECO-005 — Builder capability gate

Before generating a block, the Skill must classify the request into one of four categories:

1. **SDK-supported now** — existing public contracts are sufficient.
2. **SDK-supported but authoring-limited** — runtime/model work, but a generic Flow/Flusso authoring capability is still missing.
3. **SDK extension required** — a reusable public contract must be extended before the block can be supported safely.
4. **Core-only capability** — the request changes global Flujo semantics and must not be disguised as an external package.

The Skill must not silently patch the core to satisfy categories 3 or 4.

The classification may be mixed across runtime, persistence, Flow Add and Flusso
authoring. Every request, including a simple block, must first recover context,
produce a block specification, implementation plan and validation plan, undergo
human review, and receive explicit `🙆🏻` approval before generation. A C/D request
stops with the smallest explained SDK/core extension plan.

### BLKECO-006 — Inspector → Fluo → Flow → Flusso remains the single authoring path

The Godot Inspector remains the entry point for container selection. It does not gain a duplicate block list.

- **Inspector** selects the existing container by stable ID.
- **Fluo** owns the contextual drawer.
- **Flow** lists, selects, adds, moves and removes blocks.
- **Flusso** configures the selected block.

External blocks must eventually participate in this same path rather than opening a parallel editor surface.

### BLKECO-007 — Flow must consume generic catalog/factory capabilities

The normal Flow Add path must evolve from direct built-in-registry creation to a generic authoring adapter that can consume `FlowEditorBlockCatalog` and `FlowExternalBlockFactory` while preserving current integrated behavior.

External package support must not be implemented as a growing set of `if package_id == ...` or concrete block-type branches.

All structural editor mutations remain undoable through the owning `PVController` context and existing editor-command boundaries.

### BLKECO-008 — Flusso configuration is generic by default

A compatible block must be configurable in Flusso without requiring a new concrete-type branch in the central editor.

The approved D4-A boundary is defined in [FlowBlock Property Presentation Contract](flow_block_property_presentation_contract.md): limited Godot property reflection plus optional declarative `block_property_presentation.json` metadata. The script remains the source of property type, default value and persistence. Metadata may describe safe presentation intent such as order, label, tooltip or an approved generic presentation kind, but it must not execute callbacks or invent properties absent from the script. The descriptor boundary is UI-independent so a future runtime debugger can reuse it without editor APIs.

A request that cannot be represented by the common renderer is classified as `SDK extension required`; it does not justify arbitrary package-owned editor widgets in v1.

### BLKECO-009 — Theme belongs to the Fluo host

Standard block packages do not install or own the editor Theme. Reusable Fluo/Flow/Flusso host components own semantic visual roles for block rows, fields, buttons, diagnostics, selection, focus, disabled state and other common states.

A block may expose declared presentation metadata allowed by contract, but it does not restyle the entire editor.

### BLKECO-010 — Motion belongs to the Fluo host

Standard block packages do not implement their own drawer, focus, row or field animations.

The host owns Motion state, transition start/cancel rules, focus timing, rebuild invalidation and input policy. Motion is editor-only presentation state and never persistent `FlowGraph` state.

The minimum Motion contract must exist before `flujo-block-builder v1` is considered ready. Exact durations, easing curves and decorative microanimations may be changed later without modifying block packages.

### BLKECO-011 — Container layout and interactive geometry remain authoritative

Godot Containers remain responsible for logical layout. Motion may use Godot 4.7 offset transforms only when tests demonstrate that visual placement, hitboxes, focus, mouse filtering, touch and scroll remain consistent with the intended interaction.

A visual-only transform must not be assumed to move input geometry. Interactive controls that move visually require an explicitly verified input strategy.

### BLKECO-012 — Provenance is declared, not cryptographic

Every distributable package must be able to declare provenance so users can distinguish official Mercury content from user/community content.

The provenance model must distinguish **author** from **publisher** because the creator and distributor may differ.

Provenance v1 is a human/auditable declaration only. It must not be presented as cryptographic authenticity, verification, safety or tamper evidence.

The exact serialized `provenance.json` shape remains a separate approval before implementation.

### BLKECO-013 — Manifest v1 remains minimal

`manifest_version = 1` keeps its current implemented fields. Provenance, editor presentation metadata, package dependencies, permissions, signatures, checksums, marketplace metadata and similar future concerns are not added to manifest v1 by implication.

Any new serialized contract must either use an explicitly approved sidecar or a separately versioned manifest/schema change.

### BLKECO-014 — Missing packages never trigger silent substitution or deletion

If a saved graph references a block whose package/script is unavailable, Flujo must not silently replace it with another block, infer identity from the display name, or delete the user's data.

The persistent origin/placeholder representation required for safe recovery is deliberately **not yet approved**. It belongs to D7 and may require an explicit schema migration.

### BLKECO-015 — First external dogfooding block is deliberately simple

The first real distributable external block after D5 must be a simple class-A block, preferably derived from `FlowOutputBlock`, with deterministic output and no navigation, node access or package dependencies.

Its purpose is to prove the complete pipeline:

`package → manifest → provenance → validation → catalog → factory → Flow → Flusso → persistence → runtime → deletion independence`

The future `IF` block is explicitly outside this first proof.

### BLKECO-016 — IF requires its own specification cycle

The future `IF` block must not be generated opportunistically while building the SDK or Skill.

Its delivery starts only after the standard block path is proven and follows:

`SPECIFICATION → PLAN → maintainer approval → IMPLEMENTATION → TESTS`

Historical IF research may inform that specification but does not automatically become the final contract.

### BLKECO-017 — Official-block migration is gradual and compatibility-first

Migration of current integrated blocks to Mercury packages occurs one block at a time after the external package path is proven.

No migration may break persisted script paths, block IDs, graph schemas, existing scenes or supported project loading. Compatibility shims or explicit migrations remain until historical references are safely supported.

Deleting one official package must not delete or disable unrelated official or user packages.

### BLKECO-018 — Public package code remains portable

Runtime block scripts remain outside `addons/vp_flujo/`, use portable Godot APIs and do not depend on `EditorInterface`, `EditorUndoRedoManager`, editor Controls or absolute filesystem paths.

The D4-A property descriptor and data-only presentation metadata are designed for
safe runtime reuse, but they do not make the future Debug Panel a current runtime
dependency. The future panel requires a separate runtime access, activation and
write-back contract.

### BLKECO-019 — FlowBlocks are container-agnostic

A `FlowBlock` is independent from the container that hosts it. A block is defined
once and preserves the same behavior in compatible `Process`, `Timer`, `State
Machine`, future `IF`, future `While`, future `Do` / `Do While`, future `For`, and
other compatible `FlowBlock` containers. The container controls when and how its
sequence executes; the block preserves its own behavior contract.

The public package path must not generate container-specific variants such as
`ProcessMyBlock`, `TimerMyBlock` or `IfMyBlock`.

### BLKECO-020 — Control-flow blocks remain public custom blocks

`IF`, `While`, `Do` / `Do While` and `For` are custom blocks. They must eventually
be created through `flujo-block-builder` as dogfood users of the public Block SDK,
with the same planning, capability and explicit approval gates as every other
custom block. They must not receive private block-creation paths merely because
they implement control flow.

IF remains unimplemented and follows its own specification cycle. No sufficiently
complete approved specification has been recovered for While, Do / Do While or
For; their fields, body representation, termination rules, navigation semantics
and persistence contract must not be invented.

## Explicitly unresolved decisions

The following are **not** decided by this D0 contract and require later maintainer approval before implementation:

1. the final serialized shape of `provenance.json`, including exact `author_*`, `publisher_*`, version and source fields;
2. localization rules and runtime export/access policy for the future Debug Panel,
   which are not covered by the D4-A property-presentation contract;
3. the persistent representation used when a package disappears: per-block origin, graph-side map, placeholder/envelope, or an approved combination;
4. the exact package ID, type ID, visible name and message for any future dogfooding block beyond the approved FPrint Guardería slice;
5. touch target thresholds, reduced-motion defaults and the Android device matrix for final visual acceptance;
6. the promotion/install API for moving an incubated block into an official Mercury distribution;
7. any graph schema migration needed for package origin/recovery.

The former legacy-surface decision is resolved by the Guardería editor cleanup:
the plugin does not production-mount the visible Flujo dock or register `Open
Fluo (POC)`, while `vp_flujo_dock.gd` remains available for isolated
compatibility coverage.

- every approved architectural decision above is stated as a requirement rather than an implementation claim;
- every unresolved representation remains explicitly unresolved;
