# Typed Variables Contract

## Status and scope

This contract defines the approved Iteration 7 plan for typed variables. It does not implement runtime execution, schema changes, or Inspector changes by itself. It applies to the persistent `FlowVariableDefinition` resources already present in schema 2 and schema 3 `FlowGraph` collections.

Iteration 6 implemented schema 3 structure, method-call references, and optional method return declarations. Argument bindings, value sources, return blocks and transport, conversions, cycle validation, execution, timers, script invocation, and schema 3 Constructor or Method authoring remain outside this iteration.

## Current implemented baseline

- `FlowVariableDefinition` already has a stable internal ID, display name, `Scope`, `Binding`, `ValueType`, typed default fields, note, persistence flag, `owner_container_id`, and `global_variable_id`.
- Schema 2 and schema 3 use the same ordered nullable `FlowGraph.variables` collection. Existing validation, deep duplication, atomic schema 2 to 3 migration, `ResourceSaver`, and `PackedScene` coverage preserve compatible variable data.
- `FlowVariableDefinition.ValueType` is already reused directly by method parameter and optional return declarations. This does not give methods variable ownership, scope, binding, or runtime-value behavior.
- Schema 2 Inspector editing is implemented. Schema 3 variable editing is not implemented yet.

## Iteration 7 requirements

- **TVAR-001 — Canonical taxonomy:** `FlowVariableDefinition.ValueType` remains the single canonical variable taxonomy with exactly `BOOL`, `INT`, `FLOAT`, `STRING`, `VECTOR2`, `VECTOR3`, and `COLOR`, in that order and with their existing numeric values. No alias, parallel enum, or replacement taxonomy is introduced.
- **TVAR-002 — Godot value correspondence:** the canonical members correspond directly to Godot `bool`, `int`, `float`, `String`, `Vector2`, `Vector3`, and `Color` Variant values. This iteration introduces no `Variant` catch-all type.
- **TVAR-003 — Typed defaults and nullability:** the current defaults remain `false`, `0`, `0.0`, `""`, `Vector2.ZERO`, `Vector3.ZERO`, and `Color.WHITE`. A variable has no nullable typed value in this iteration. A `null` collection position remains structural absence, not a variable value.
- **TVAR-004 — Stable identity and references:** internal IDs generated by `FlowId` are the only persistent references. Display names, collection indexes, paths, and presentation order are never identity. `owner_container_id` and `global_variable_id` remain stored literally for validation and diagnostics.
- **TVAR-005 — Schema compatibility:** schemas 2 and 3 retain their existing variable representation and semantics without reinterpretation, synchronization, or implicit migration. Schema 1 remains separate. A change to `schema_version` requires an explicit tested migration.
- **TVAR-006 — Compatible validation:** validation may add deterministic checks only when they accept all data valid under the existing schema 2/3 contract. It must preserve invalid values and use stable codes, paths, related IDs, and traversal order. Strict mandatory scope, binding, or owner combinations are deferred because existing data does not establish those semantics unambiguously.
- **TVAR-007 — Ownership and scope safety:** variables remain graph-owned resources. Existing local-owner and global-variable links are graph-local ID references; they do not become `Node`, `NodePath`, `Resource`, `Object`, or `Callable` references. Runtime resolution and mutable values remain per-controller future concerns.
- **TVAR-008 — Deep duplication:** graph duplication must preserve each of the seven typed default values, array order, and deliberate `null` positions while giving copied valid resources new IDs through the existing graph-wide old-ID to new-ID map. Valid internal references remap only when both endpoints belong to the copy; unknown or invalid values remain literal for diagnostics.
- **TVAR-009 — Persistence:** every canonical type and default must survive `ResourceSaver` and `PackedScene` round trips, including schema 2 to 3 migration compatibility. Tests must demonstrate that no type member or numeric serialization value changed.
- **TVAR-010 — Schema 3 variable Inspector:** add an editor-only, undoable workflow for the existing schema 3 `variables` collection. It must use the owning `PVController` as the `EditorUndoRedoManager` scene context, retain stable-ID selection, preserve `null` positions, and never make editor APIs a runtime dependency.
- **TVAR-011 — Basic keyboard accessibility:** the schema 3 variable workflow must provide predictable focus and keyboard operation for its visible controls. Enter and Escape behavior, selection changes, undo/redo, save/reopen, and keyboard navigation require automated coverage where possible and manual Godot review.
- **TVAR-012 — Deferred context menu:** a context menu is not part of Iteration 7. Its command set, focus behavior, localization, and accessibility rules require a separate approved specification.
- **TVAR-013 — Forbidden persistent object references:** this iteration adds no persistent `Node`, `NodePath`, `Resource`, `Object`, `Callable`, raw pointer, or custom garbage collector. Godot-managed `Resource` and `RefCounted` lifetimes plus stable IDs remain the applicable model strategy.
- **TVAR-014 — Explicit schema 4 boundary:** symbolic enumerators, persistent object references, nullable typed values, and value-source resources require their own contract and an explicit schema 4 migration. They must not be introduced as hidden compatibility changes to schema 3.
- **TVAR-015 — Public language and user guidance:** public plugin metadata, visible editor text, and user-facing documentation must be English by the end of the iteration, while localization-ready tooltips remain separate. The pre-alpha warning must remain clear and friendly. After the variable interface is implemented, add a simple user guide separate from this technical contract. ChatGPT and Codex may assist, but Flujo remains provider-independent and authorized human review retains approval authority.

## Planned deliveries

1. **Contract:** approve this contract, the compatibility boundary, and the numbered acceptance criteria.
2. **Validation (implemented):** deterministic validation now rejects numeric values outside the declared `Scope`, `Binding`, and `ValueType` members without changing stored values. Variable metadata is checked after its resource identity and before deferred variable-reference diagnostics; parameter metadata follows parameter identity and name validation; return metadata follows return identity. New diagnostics are `invalid_variable_scope`, `invalid_variable_binding`, and `invalid_value_type`, with the metadata-property path and owning resource ID as `related_id`. Existing diagnostic order remains unchanged when metadata is valid.
3. **Persistence and duplication:** extend smoke and persistence regressions for all seven types, defaults, IDs, references, order, `null` positions, migration, and independence.
4. **Schema 3 Inspector:** implement variable-only schema 3 authoring with scene-context undo/redo; do not add Constructor or Method authoring.
5. **Keyboard and visual review:** add focused keyboard/focus regressions and manually review empty state, edits, undo/redo, save/reopen, selection, and navigation.
6. **English, guide, and final audit:** translate remaining public Spanish text and comments, add the separate user guide after interface completion, audit traceability, and record available metrics.

## Deferred work

- Symbolic enumerators and their owned definitions or collections.
- Nullable typed values, persistent object references, and a common value-source abstraction.
- `FlowMethodArgumentBinding`, `FlowMethodReturnBlock`, argument and return transport, implicit or explicit conversions, recursion and call-cycle validation.
- Runtime execution, timers, script invocation, scene bindings, visual connections, and Constructor or Method schema 3 authoring.
- Context menus beyond the existing approved editor workflows.

## Verification and acceptance

Each delivery must trace its `TVAR` requirement to implementation, test or manual review, and commit. Required evidence includes deterministic validation diagnostics, deep-duplication independence, all-seven-type `ResourceSaver` and `PackedScene` coverage, schema-boundary coverage, headless editor loading, model smoke tests, focused editor tests, and visual review whenever visible behavior changes. Measurements use the Engineering Flow Metrics policy; unavailable evidence is recorded as `unknown` or `not measured`.
